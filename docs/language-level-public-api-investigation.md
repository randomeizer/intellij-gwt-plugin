# GWT client language levels: public API investigation for #52

Investigated 2026-11-12 against IntelliJ IDEA **263.7307.200 / 2026.3**, the exact configured SDK. Production integration is unchanged; active runtime probes were added. No production workaround or external post was made.

## Outcome

**No supported, complete public replacement was found for `JavaLanguageLevelPusherCustomizer` in this SDK.** The remaining three verifier findings identify the internal interface and its two overridden callbacks. Removing that registration without an equivalent platform seam would lose per-client language levels. A separate property pusher, a loaded-PSI override, and the modern Java syntax provider each cover only part of the behavior; none supplies the GWT diagnostic customization plus the level consistently used by parsing, resolution, and indexing. This is an evidence-based limitation of the inspected SDK, not a proof that every possible future JetBrains API lacks such support. [Issue #52](https://github.com/randomeizer/intellij-gwt-plugin/issues/52), [existing internal SPI](https://github.com/JetBrains/intellij-community/blob/idea/263.7307.200/java/java-analysis-impl/src/com/intellij/openapi/roots/impl/JavaLanguageLevelPusherCustomizer.java#L14-L44).

There is a second, independent finding: **the existing GWT diagnostic callback appears disconnected from the 263 Java highlighter**. Its old method remains on the pusher, but the modern unsupported-feature diagnostic constructs the standard message directly. Static inspection found no Java SDK caller of the old callback beyond the pusher/customizer pair. The active runtime highlighting probe now confirms that this path does not call the legacy callback or append the GWT suffix; this is baseline behavior, not a migration regression. [Current unsupported-feature diagnostic](https://github.com/JetBrains/intellij-community/blob/idea/263.7307.200/java/codeserver/highlighting/src/com/intellij/java/codeserver/highlighting/errors/JavaErrorKinds.java#L188-L200).

## Behavior that must remain

`GwtLanguageLevelPusher.getImmediateValue` finds the module/facet, compares effective module and configured client levels, and returns the client level for files classified as GWT source or super-source only when the levels differ. The comparison allows either a lower or higher client level. Other files return null and inherit IntelliJ's normal level. The diagnostic callback adds the bundle suffix identifying the GWT facet for classified client/super-source files. [Plugin implementation](https://github.com/randomeizer/intellij-gwt-plugin/blob/615b632e/src/org/randombits/intellij/gwt/psi/GwtLanguageLevelPusher.java), [bundle](https://github.com/randomeizer/intellij-gwt-plugin/blob/615b632e/resources/messages/GwtBundle.properties).

`GwtSourcePathsRefresher` collects source and super-source paths from GWT modules, preserves include/exclude rules, invalidates the super-source cache, and queues updates for roots/XML/VFS changes. After path changes or a forced refresh it calls `JavaLanguageLevelPusher.pushLanguageLevel(project)`. The facet editor forces refresh after compiler parameters change the effective client language level. Normal GWT source classification excludes test source content; super-source classification follows its own existing path rules. A replacement must preserve those actual rules rather than treating every Java file in the IDE module as client code. [Refresher](https://github.com/randomeizer/intellij-gwt-plugin/blob/615b632e/src/org/randombits/intellij/gwt/psi/GwtSourcePathsRefresher.java), [facet editor](https://github.com/randomeizer/intellij-gwt-plugin/blob/615b632e/src/org/randombits/intellij/gwt/facet/GwtFacetEditor.java#L538-L546).

The client level comes from the facet's explicit `-sourceLevel`, falling back to the selected GWT SDK version's supported level. Compiler behavior remains independently important: JPS passes the facet compiler parameters, the dev command line passes explicit sourceLevel, and Gradle obtains its sourceLevel argument from the configured effective client level. Editor API availability does not authorize changing these paths. [Facet configuration](https://github.com/randomeizer/intellij-gwt-plugin/blob/615b632e/src/org/randombits/intellij/gwt/facet/GwtFacetConfiguration.java#L181-L192), [parameter extraction](https://github.com/randomeizer/intellij-gwt-plugin/blob/615b632e/jps-plugin/src/org/randombits/intellij/gwt/jps/model/impl/GwtModuleExtensionProperties.java#L38-L47), [JPS builder](https://github.com/randomeizer/intellij-gwt-plugin/blob/615b632e/jps-plugin/src/org/randombits/intellij/gwt/jps/build/GwtBuilder.java#L177-L194), [dev command](https://github.com/randomeizer/intellij-gwt-plugin/blob/615b632e/src/org/randombits/intellij/gwt/run/GwtCommandLineState.java#L409-L412), [Gradle execution](https://github.com/randomeizer/intellij-gwt-plugin/blob/615b632e/src/org/randombits/intellij/gwt/gradle/GwtGradleExecutionEnvironmentProvider.java#L120).

### Why a separate file pusher does not replace the Java pusher

The built-in Java pusher owns a private persistent `FilePropertyKey<LanguageLevel>`. Its public getter exposes that key, but its file/directory values are produced by the built-in pusher and its internal customization callback. Java resolution reads the built-in pusher; Java indexing flavor also reads it. An extension using its own key is not consulted by those readers. [Private key and customization](https://github.com/JetBrains/intellij-community/blob/idea/263.7307.200/java/java-analysis-impl/src/com/intellij/openapi/roots/impl/JavaLanguageLevelPusher.java#L23-L63), [resolve implementation](https://github.com/JetBrains/intellij-community/blob/idea/263.7307.200/java/java-impl/src/com/intellij/psi/impl/JavaPsiImplementationHelperImpl.java#L287-L310), [indexing flavor](https://github.com/JetBrains/intellij-community/blob/idea/263.7307.200/java/java-impl/src/com/intellij/index/JavaFileIndexingFlavor.java#L12-L20).

The updater processes each applicable pusher in sequence and writes each computed value. Its lookup order is immediate per-file value, module value when supplied, inherited parent/project value, default. There is no cross-pusher highest-priority Java language value arbitration. EP ordering can order callbacks, but does not define supported multiple ownership of the built-in Java key. A second writer reusing that key would compete with the built-in writer, including built-in-only `pushLanguageLevel` refreshes, and still would not supply the diagnostic hook. That is an unsupported writer trick rather than a demonstrated public replacement. [Updater application and lookup](https://github.com/JetBrains/intellij-community/blob/idea/263.7307.200/platform/lang-impl/src/com/intellij/openapi/roots/impl/PushedFilePropertiesUpdaterImpl.kt#L299-L355), [lookup details](https://github.com/JetBrains/intellij-community/blob/idea/263.7307.200/platform/lang-impl/src/com/intellij/openapi/roots/impl/PushedFilePropertiesUpdaterImpl.kt#L441-L457).

The public static `pushLanguageLevel(project)` remains useful to invoke the existing push, but supplies no provider argument and therefore cannot substitute for the removed customization. **There is no `JavaLanguageLevelPusher.getInstance()` in this SDK.** The class locates its built-in EP instance internally. [Exact pusher declaration](https://github.com/JetBrains/intellij-community/blob/idea/263.7307.200/java/java-analysis-impl/src/com/intellij/openapi/roots/impl/JavaLanguageLevelPusher.java#L23-L36).

### Why the public PSI key is incomplete

The key belongs on the **`PsiFile`**, not the `VirtualFile`. `PsiJavaFileBaseImpl.getLanguageLevelInner()` checks `PsiUtil.FILE_LANGUAGE_LEVEL_KEY` user data on itself before consulting the project helper. However `getLanguageLevel()` separately caches the result in a private lazy key, and `clearCaches()` clears that cache. Setting the public key after initial access does not itself invalidate the cached result. [PSI reader/cache](https://github.com/JetBrains/intellij-community/blob/idea/263.7307.200/java/java-psi-impl/src/com/intellij/psi/impl/source/PsiJavaFileBaseImpl.java#L622-L704).

In contrast, `PsiResolveHelper.getEffectiveLanguageLevel(VirtualFile)` delegates to the Java implementation helper, which reads the built-in persistent pusher key before module/project fallback. Java indexing flavor reads that persistent value independently of the open PSI instance. Thus a loaded PSI file can say Java 8 while its virtual file's effective level and index flavor still say Java 17. The key does not install a lifecycle provider for files created during indexing, closed/reopened PSI instances, source-root changes, or reloads. Calling a general reparse operation does not establish that missing provider. [Resolve delegation](https://github.com/JetBrains/intellij-community/blob/idea/263.7307.200/java/java-psi-impl/src/com/intellij/psi/impl/source/resolve/PsiResolveHelperImpl.java#L302-L305), [effective level](https://github.com/JetBrains/intellij-community/blob/idea/263.7307.200/java/java-impl/src/com/intellij/psi/impl/JavaPsiImplementationHelperImpl.java#L287-L310), [index flavor](https://github.com/JetBrains/intellij-community/blob/idea/263.7307.200/java/java-impl/src/com/intellij/index/JavaFileIndexingFlavor.java#L12-L20).

This does not mean the public key is forbidden or incapable of affecting a physical PSI file. It means it is not enough to satisfy #52's existing behavior contract consistently.

### Why the modern syntax/feature extensions are incomplete

`JavaLanguageLevelProvider.getLanguageLevel(SyntaxNode)` is documented for Java lazy parsers. The implementation selects the first provider and otherwise uses the highest level; there is no nullable abstention/chain in this declaration, no direct project/virtual-file input, and no write to persistent Java file properties. Even with a sound SyntaxNode-to-file mapping, this cannot alone change `PsiJavaFile.getLanguageLevel`, virtual-file effective level, indexing flavor, or diagnostic text. [Provider implementation](https://github.com/JetBrains/intellij-community/blob/idea/263.7307.200/java/java-syntax/src/com/intellij/java/syntax/element/JavaLanguageLevelProvider.kt#L11-L26), [EP declaration](https://github.com/JetBrains/intellij-community/blob/idea/263.7307.200/java/java-syntax/resources/intellij.java.syntax.xml#L12-L16).

`LanguageFeatureProvider` affects only features flagged customizable, after the baseline language-level sufficiency check. `PsiUtil.isAvailable` returns false for insufficient language level before invoking providers. Ordinary features such as generics and records cannot all be modeled by this seam, and it does not change language level or diagnostic description. [Availability algorithm](https://github.com/JetBrains/intellij-community/blob/idea/263.7307.200/java/java-psi-api/src/com/intellij/psi/util/PsiUtil.java#L1285-L1296), [feature customization contract](https://github.com/JetBrains/intellij-community/blob/idea/263.7307.200/java/java-syntax/src/com/intellij/pom/java/JavaFeature.kt#L353-L385).

## Diagnostic baseline caveat

The current plugin callback returns the normal message with a GWT facet suffix. IntelliJ's old pusher getter still delegates to that callback. However the 263 `JavaErrorKinds.UNSUPPORTED_FEATURE` description directly builds its message from the feature name and `PsiUtil.getLanguageLevel(element)`. The matching source contains no customizer consultation at that point; the exact Java SDK class scan found no consumer of the old pusher message method. [Plugin callback](https://github.com/randomeizer/intellij-gwt-plugin/blob/615b632e/src/org/randombits/intellij/gwt/psi/GwtLanguageLevelPusher.java#L46-L59), [pusher delegation](https://github.com/JetBrains/intellij-community/blob/idea/263.7307.200/java/java-analysis-impl/src/com/intellij/openapi/roots/impl/JavaLanguageLevelPusher.java#L92-L96), [new diagnostic](https://github.com/JetBrains/intellij-community/blob/idea/263.7307.200/java/codeserver/highlighting/src/com/intellij/java/codeserver/highlighting/errors/JavaErrorKinds.java#L188-L200).

Inference: an actual record/lambda unsupported-feature highlight may already lack the GWT suffix before changing this plugin. A direct unit call proving that the GWT callback returns its suffix would not prove editor integration. Do not delete the callback or introduce suppression to hide this discrepancy; capture the baseline and include a supported diagnostic-description seam in the upstream request.

## Supported next steps and upstream API request shape

1. Keep the production feature and strict verifier unchanged while recording the exact public API gap in #52's branch documentation. Keep #52 open; documentation and baseline tests do not satisfy its implementation acceptance criteria.
2. Prepare a concrete upstream request, with the baseline probes above, for JetBrains to expose a supported per-file Java language-level SPI and diagnostic-description customization. Do not post externally without authorization.
3. Re-evaluate only after a supported API is supplied or the target SDK is changed deliberately; verify the actual revision rather than assuming a newer version contains it.

The smallest upstream change could be making the existing two-callback customizer a supported extension contract, with documented lifecycle/priority behavior and a repaired connection to modern unsupported-feature diagnostics. An equivalent replacement must provide:

- `Project` plus nullable `VirtualFile` context and nullable `LanguageLevel` result, with null delegating to normal module/project behavior and a documented priority before module fallback.
- Integration into the canonical persistent Java-level reader used by parsing, resolution, indexes/stubs, and unloaded files, rather than only open editor PSI.
- A public refresh/invalidation path for settings, module/project levels, and GWT XML/source-root changes, preserving already opened PSI consistency.
- A nullable message customization callback with original message, effective level, and file, actually used by modern Java unsupported-feature highlighting, so GWT-specific context is retained.
- Explicit supported annotations and dynamic extension semantics, without requiring consumers to call OverrideOnly methods or inherit Internal implementation classes.

This is a requested platform contract, **not an API that currently exists**. Until then, retaining the current feature and three disclosed Internal findings is more honest than a verifier-clean implementation that silently changes editor semantics. No reflection, competing persistent-key writer, module-wide level change, diagnostic suppression, or feature removal is proposed.

All six pass in both normal and free runtimes. They verify initial client/super-source parser levels, independent server/native file levels, equal/different levels, client/module setting changes, GWT XML source-root changes and compiler-setting independence.

Production never uses this workaround or the test-only cache reset.

The diagnostic probe delegates the working native level override through a counting test customizer and invokes actual Java highlighting at client level 8. An unsupported-feature diagnostic is produced, the legacy message callback count is **zero**, and the GWT suffix is absent. At level 8 the current parser classifies the record probe through its compact-source/unsupported-feature path; the probe checks the observed level-8 diagnostic rather than assuming a particular Java feature name.

Settings/root-refresh assertions deliberately use the native resolve/file-level consumer. A previously loaded PSI object can retain a separately cached level until reparse, so a public userdata key does not establish invalidation parity either. The initial parser-level assertions and explicit public-key probe distinguish those consumers.
