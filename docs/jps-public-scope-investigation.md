# Public JPS scope and artifact guard investigation (#50)

Investigated 2026-11-12 against the installed IDEA **263.7307.200** JARs and matching `idea/263.7307.200` upstream source. Research only: this note does not implement or claim runtime validation of the proposed guard.

## Result

The public complex-packaging substitution and ordinary directory-copy nodes can establish **build ordering**, but cannot automatically include GWT targets in a standalone **artifact-only** scope. No generic public JPS scope-extension hook was found in the inspected exact SDK. The existing IDE scope provider is the correct place to add the GWT and Java production scopes for both regular and deployment packaging elements. A standalone caller must supply those scopes explicitly under the approved output-relocation design.

An actionable failure for a missing GWT scope can use a public **`ArtifactBuildTaskProvider` PRE_PROCESSING `BuildTask`**. It can inspect `context.getScope().isWholeTargetAffected(gwtTarget)` and throw `ProjectBuildException(String)` before artifact copying. This prevents a selected artifact from silently copying stale generated output or succeeding empty when compilation was omitted. It cannot retroactively add a target to the scope or invoke its compilation. The concrete guard still needs real-JPS regression validation.

## Why ordinary directory-copy dependencies are insufficient

`BuildRunner.createCompilationScope` performs its optional transitive dependency inclusion by directly calling each selected target's `computeDependencies` with a dummy `TargetOutputIndex` whose only method returns an empty list. The standard directory-copy builder obtains dependencies solely from that index. Consequently a complex node substituted with directory-copy leaves has no GWT dependency in this early pass. The later real output index can order an already included GWT target before the artifact; ordering does not make an excluded target affected. See exact source [BuildRunner](https://github.com/JetBrains/intellij-community/blob/idea/263.7307.200/jps/jps-builders/src/org/jetbrains/jps/cmdline/BuildRunner.java), [standard packaging builders](https://github.com/JetBrains/intellij-community/blob/idea/263.7307.200/jps/jps-builders/src/org/jetbrains/jps/incremental/artifacts/builders/LayoutElementBuildersRegistry.java), and [IncProjectBuilder](https://github.com/JetBrains/intellij-community/blob/idea/263.7307.200/jps/jps-builders/src/org/jetbrains/jps/incremental/IncProjectBuilder.java).

This is independent of the initialization issue documented in [the earlier investigation](jps-public-api-investigation.md): deriving substitutions from the model before artifact-root construction solves path availability, while explicit scope contribution solves target inclusion. Both are necessary.

## Module-based targets and module-output nodes

There is a real automatic-inclusion path, but it has material semantics:

1. A standard production module-output packaging node directly contributes a Java production `ModuleBuildTarget`, without consulting the output index.
2. `ArtifactBuildTarget.computeDependencies` then expands any module-based dependency into **all** registered production targets for that module. A custom GWT `ModuleBasedTarget` would therefore be included in this early artifact dependency pass.
3. The ordinary module-output node also copies Java class output into the artifact. Adding it solely as a dependency trigger changes the artifact layout.

Sources: [ModuleOutputElementBuilder and its copy/dependency methods](https://github.com/JetBrains/intellij-community/blob/idea/263.7307.200/jps/jps-builders/src/org/jetbrains/jps/incremental/artifacts/builders/LayoutElementBuildersRegistry.java), [ArtifactBuildTarget.computeDependencies](https://github.com/JetBrains/intellij-community/blob/idea/263.7307.200/jps/jps-builders/src/org/jetbrains/jps/incremental/artifacts/ArtifactBuildTarget.java), and [BuildTargetRegistryImpl](https://github.com/JetBrains/intellij-community/blob/idea/263.7307.200/jps/jps-builders/src/org/jetbrains/jps/builders/impl/BuildTargetRegistryImpl.java). These implementation classes are evidence, not proposed production dependencies.

Changing GWT to `ModuleBasedTarget` also changes its documented contract: such targets are built whenever the IDE's Build Module action runs; targets requiring an explicit action should extend `BuildTarget` directly. GWT currently extends `BuildTarget` and depends on the module's production targets. If converted, its dependency enumeration must exclude itself to avoid a self-dependency. See [ModuleBasedTarget API](https://github.com/JetBrains/intellij-community/blob/idea/263.7307.200/jps/jps-builders/src/org/jetbrains/jps/builders/ModuleBasedTarget.java) and local `jps-plugin/src/org/randombits/intellij/gwt/jps/build/GwtBuildTarget.java`.

Java's `ModuleBuildTarget` only adds custom module targets with `isCompiledBeforeModuleLevelBuilders() == true`. Setting that flag on GWT while GWT depends on Java creates Java-to-GWT and GWT-to-Java dependencies. It is not a safe way to obtain inclusion for this compiler. Artifact dependency expansion itself does not require that flag. See [ModuleBuildTarget.computeDependencies](https://github.com/JetBrains/intellij-community/blob/idea/263.7307.200/jps/jps-builders/src/org/jetbrains/jps/incremental/ModuleBuildTarget.java).

The public `JpsModuleOutputPackagingElement` contract represents copying or packing the referenced module's output. Although its nullable `getOutputUrl()` would let a plugin invent a null-output production node to trigger dependencies without copying, no documented dependency-only semantic was found. Such a node would deliberately suppress the output its interface represents and still require the broader module-based GWT redesign. It is not established here as a supported substitute for a dependency hook. See [module-output API](https://github.com/JetBrains/intellij-community/blob/idea/263.7307.200/jps/model-api/src/org/jetbrains/jps/model/artifact/elements/JpsModuleOutputPackagingElement.java) and [production marker](https://github.com/JetBrains/intellij-community/blob/idea/263.7307.200/jps/model-api/src/org/jetbrains/jps/model/java/JpsProductionModuleOutputPackagingElement.java).

`JavaBuilderExtension` offers only encoding consideration and additional compilable module types in this SDK. It has no dependency or scope callback. `AdditionalDependenciesProvider` is absent from the inspected JPS SDK; do not assume an older similarly named hook is available. `ModuleInducedTargetType` is a skip-optimization marker, not a scope-extension callback. See [JavaBuilderExtension](https://github.com/JetBrains/intellij-community/blob/idea/263.7307.200/jps/jps-builders/src/org/jetbrains/jps/builders/java/JavaBuilderExtension.java) and [ModuleInducedTargetType](https://github.com/JetBrains/intellij-community/blob/idea/263.7307.200/jps/jps-builders/src/org/jetbrains/jps/builders/ModuleInducedTargetType.java).

## Public pre-copy guard

`ArtifactBuildTaskProvider` explicitly documents service registration under `META-INF/services/org.jetbrains.jps.builders.artifacts.ArtifactBuildTaskProvider`. Its `createArtifactBuildTasks(artifact, PRE_PROCESSING)` returns `List<? extends BuildTask>`. The SDK has no separate `ArtifactBuildTask` API. `BuildTask.build(CompileContext)` may throw `ProjectBuildException`; the message constructor is documented to stop the build and display the message as an error. Sources: [provider API](https://github.com/JetBrains/intellij-community/blob/idea/263.7307.200/jps/jps-builders/src/org/jetbrains/jps/builders/artifacts/ArtifactBuildTaskProvider.java), [BuildTask](https://github.com/JetBrains/intellij-community/blob/idea/263.7307.200/jps/jps-builders/src/org/jetbrains/jps/incremental/BuildTask.java), and [ProjectBuildException](https://github.com/JetBrains/intellij-community/blob/idea/263.7307.200/jps/jps-builders/src/org/jetbrains/jps/incremental/ProjectBuildException.java).

Exact `IncArtifactBuilder` runs PRE_PROCESSING after checking a valid artifact output path and circular artifact inclusion, and **before** processing dirty files or copying. It calls PRE_PROCESSING even when the dirty-file holder is empty. `IncProjectBuilder.buildTarget` invokes the selected target builder with a holder; it does not itself require dirty files before that invocation. Thus a selected, valid artifact can reject the missing scope before stale files are copied, including no-change rebuild requests. Source: [IncArtifactBuilder](https://github.com/JetBrains/intellij-community/blob/idea/263.7307.200/jps/jps-builders/src/org/jetbrains/jps/incremental/artifacts/IncArtifactBuilder.java) and [IncProjectBuilder](https://github.com/JetBrains/intellij-community/blob/idea/263.7307.200/jps/jps-builders/src/org/jetbrains/jps/incremental/IncProjectBuilder.java).

`CompileContext.getScope()` and `CompileScope.isWholeTargetAffected(BuildTarget)` are public and unannotated. The latter means the complete target is included; checking only `isAffected` could accept a partial-file scope unsuitable for a whole GWT compilation. A task can resolve each plugin-owned packaging element's module and construct the equivalent plugin-owned GWT target for this query. Empty GWT module selections should be handled consistently with the existing packaging contract, rather than inventing a requirement to compile modules that the artifact does not select. Sources: [CompileContext](https://github.com/JetBrains/intellij-community/blob/idea/263.7307.200/jps/jps-builders/src/org/jetbrains/jps/incremental/CompileContext.java) and [CompileScope](https://github.com/JetBrains/intellij-community/blob/idea/263.7307.200/jps/jps-builders/src/org/jetbrains/jps/incremental/CompileScope.java).

Annotation verification matters: `CompileScope` contains an internal deprecated **File overload** of `isAffected`; this does not make `isWholeTargetAffected` internal. Exact `javap -p -v` inspection confirmed the proposed provider method, `BuildTask.build`, `CompileContext.getScope`, and `CompileScope.isWholeTargetAffected` lack `ApiStatus.Internal`. The provider, task, and exception classes also lack Internal/NonExtendable annotations, and `org.jetbrains.jps.builders.artifacts` / `org.jetbrains.jps.incremental` have no package-info class in the owning JAR. No use of artifact instruction builders is needed for this guard.

The guard must cover regular and deployment-only GWT packaging elements, nested substitutions, and referenced artifact layouts as appropriate. For the IDE provider, local `GwtBuildTargetScopeProvider.getFacetsIncludedInArtifacts` currently visits only `GwtCompilerOutputElementType`; it needs equivalent deployment-element discovery. Existing explicit GWT and Java scope construction can otherwise remain the authority for IDE builds.

## Exclude relocated output from IDE indexing

The final implementation can use public legacy `DirectoryIndexExcludePolicy`; no modern contributor dependency is needed. All seven artifact integration tests pass in both normal and free modes, including inherited/custom output-path changes and facet removal. The fixture establishes the parent directory's VFS children **before** creating the missing generated directory. The earlier missing-root failures therefore did not establish a production exclusion defect.

### Public policy API and invalidation

`DirectoryIndexExcludePolicy` is an **interface** annotated `ApiStatus.OverrideOnly`, explicitly intended to be implemented and registered as `directoryIndexExcludePolicy` in `plugin.xml`. Override its default `String[] getExcludeUrlsForProject()`; the contract explicitly accepts URLs for directories that do not exist yet. Avoid its `EP_NAME` constant and static `getExtensions` helper (Internal), and avoid the deprecated-for-removal module/SDK-root methods. Source: [DirectoryIndexExcludePolicy](https://github.com/JetBrains/intellij-community/blob/idea/263.7307.200/platform/projectModel-impl/src/com/intellij/openapi/roots/impl/DirectoryIndexExcludePolicy.java).

An implementation can receive `Project` through its constructor, enumerate modules, and obtain each nullable production URL through public `CompilerModuleExtension.getInstance(module).getCompilerOutputUrl()`. Pure URL/path computation derives `<production-parent>/.intellij-gwt`. No filesystem query, VFS refresh, directory creation, or facet lookup is needed inside the policy getter. Excluding the reserved container for all modules also covers plugin leftovers after facet removal and avoids facet-only invalidation dependencies. Exact `CompilerModuleExtensionBridge` resolves inherited project output and custom per-module output in that URL getter. Sources: [CompilerModuleExtension](https://github.com/JetBrains/intellij-community/blob/idea/263.7307.200/platform/projectModel-api/src/com/intellij/openapi/roots/CompilerModuleExtension.java) and [CompilerModuleExtensionBridge](https://github.com/JetBrains/intellij-community/blob/idea/263.7307.200/java/java-impl/src/com/intellij/workspaceModel/ide/legacyBridge/impl/java/CompilerModuleExtensionBridge.kt). Exact bytecode confirms the consumed public module-extension API/methods are not Internal; implementation classes are evidence only.

`NonIncrementalContributors` integrates these policy URLs into `WorkspaceFileIndex`; nonexistent URLs are registered for later directory creation. Normal root changes invalidate the policies: both `ProjectRootManagerComponent.fireBeforeRootsChangeEvent` and `fireRootsChangedEvent` call `indexData.resetCustomContributors()`, which marks the policy cache stale and recomputes its URLs on demand. `NonExistingWorkspaceRootsRegistry` analyzes creation events; `RootsChangeWatcher` surrounds its change applier with the root events. No manual calls to these internal implementation APIs are needed in plugin code. Sources: [NonIncrementalContributors](https://github.com/JetBrains/intellij-community/blob/idea/263.7307.200/platform/projectModel-impl/src/com/intellij/workspaceModel/core/fileIndex/impl/NonIncrementalContributors.kt), [ProjectRootManagerComponent](https://github.com/JetBrains/intellij-community/blob/idea/263.7307.200/platform/lang-impl/src/com/intellij/openapi/roots/impl/ProjectRootManagerComponent.kt), [NonExistingWorkspaceRootsRegistry](https://github.com/JetBrains/intellij-community/blob/idea/263.7307.200/platform/projectModel-impl/src/com/intellij/workspaceModel/core/fileIndex/impl/NonExistingWorkspaceRootsRegistry.kt), and [RootsChangeWatcher](https://github.com/JetBrains/intellij-community/blob/idea/263.7307.200/platform/lang-impl/src/com/intellij/workspaceModel/ide/impl/legacyBridge/watcher/RootsChangeWatcher.kt).

### Test actual VFS creation rather than first discovery

The integration fixture creates output on disk, then calls `LocalFileSystem.refreshAndFindFileByIoFile`. If the parent has not loaded its children, the SDK can discover that child as an initial filesystem lookup without firing a creation event. Exact `VirtualDirectoryImpl.findInPersistence` loads and caches the child; `findChildImpl` instead returns the cached-absence sentinel when all children are loaded, allowing the refresh path to call `createChildAndFireCreationEvent`. Source: [VirtualDirectoryImpl](https://github.com/JetBrains/intellij-community/blob/idea/263.7307.200/platform/vfs-impl/src/com/intellij/openapi/vfs/newvfs/impl/VirtualDirectoryImpl.java).

The fixture must therefore load the actual production parent and call `parent.getChildren()` **before** physically creating `.intellij-gwt`, then create/refresh the container and generated file. This establishes the VFS baseline and exercises the missing-root creation event that the exclusion registry consumes. This single-variable change made the original failing normal-mode scenario pass with the original public legacy policy. Waiting afterward cannot manufacture an event already bypassed by initial discovery; neither `UIUtil.dispatchAllInvocationEvents()` nor `VfsTestUtil.syncRefresh()` alone fixed that fixture.

Public `VfsTestUtil.syncRefresh()` remains the appropriate synchronization helper after external filesystem mutation: it refreshes VFS under the appropriate write/EDT context and waits for queued/running indexing work through `IndexingTestUtil`. It complements the pre-mutation VFS baseline. Sources: [VfsTestUtil](https://github.com/JetBrains/intellij-community/blob/idea/263.7307.200/platform/testFramework/src/com/intellij/testFramework/VfsTestUtil.java) and [IndexingTestUtil](https://github.com/JetBrains/intellij-community/blob/idea/263.7307.200/platform/testFramework/src/com/intellij/testFramework/IndexingTestUtil.kt). The cached exact-SDK test-framework sources agree with these matching-tag sources.

Required verification: inherited and custom output, exclusion before/after actual generated-directory creation, output URL changes after an index lookup, facet removal, and full normal/free-mode tests. Distinguish those implementation results from this research's source/bytecode inspection.

### Modern alternative is public but unnecessary here

`WorkspaceFileIndexContributor<E>` and `WorkspaceFileSetRegistrar.registerExcludedRoot(VirtualFileUrl, WorkspaceEntity)` provide a public entity-based alternative. The contributor is OverrideOnly and its package is **Experimental**, not Internal. The platform uses separate `JavaModuleSettingsEntity` and `JavaProjectSettingsEntity` contributors for compiler output; actual Java entity names in 263 are under `com.intellij.java.workspace.entities`. A plugin could similarly register custom output's parent container and inherited project output's `production/.intellij-gwt`. However, the same fixture baseline issue also affected this alternative, so it provided no demonstrated fix and is not needed for the final policy design. Sources: [contributor/registrar API](https://github.com/JetBrains/intellij-community/blob/idea/263.7307.200/platform/projectModel-impl/src/com/intellij/workspaceModel/core/fileIndex/WorkspaceFileIndexContributor.kt), [Experimental package status](https://github.com/JetBrains/intellij-community/blob/idea/263.7307.200/platform/projectModel-impl/src/com/intellij/workspaceModel/core/fileIndex/package-info.java), and [platform compiler-output contributors](https://github.com/JetBrains/intellij-community/blob/idea/263.7307.200/java/compiler/impl/src/com/intellij/openapi/roots/impl/CompilerOutputWorkspaceFileIndexContributor.kt).
