# Public repository configuration bridge for JPS (#50)

Investigated 2026-11-12 against the downloaded IDEA **263.7307.200** binaries and matching `idea/263.7307.200` upstream sources. Research only: this note does not establish that the proposed implementation passes Plugin Verifier or functional tests.

## Result

Use **per-build scope user data**, rather than a launch argument or a temporary bridge file, to pass a plugin-owned repository DTO from the IDE to JPS. Keep authentication resolution inside JPS. The relevant configuration, transport, acquisition, retry, progress and authentication-provider entry points are public in this SDK; two provider APIs remain explicitly Experimental. No production reference to the Internal JPS repository model or `JpsMavenSettings` is necessary.

Add a second public project serializer for the existing `RemoteRepositoriesConfiguration` component to obtain the same repository information for standalone builds. Use public `JpsModelSerializationDataService.getPathVariableValue(global, "MAVEN_REPOSITORY")` for the existing global local-repository override, followed by a plugin-owned implementation of the native Maven settings/environment fallback. This preserves both IDE builds and standalone persisted project configuration without writing credentials into project files or builder parameters.

## Concrete per-build transport

`CompileScope` extends public `ExportableUserDataHolder`. `ExportableUserDataHolderBase.exportUserData()` exports its non-null user-data entries. In the exact `CompileDriver.compileInExternalProcess` implementation, `getBuildScopes(...)` runs scope providers **before** the scope's data is exported. The driver converts each key and value with `toString()` and sends the resulting string map as builder parameters. JPS exposes public `CompileContext.getBuilderParameter(String)`. Sources: [CompileScope](https://github.com/JetBrains/intellij-community/blob/idea/263.7307.200/java/compiler/openapi/src/com/intellij/openapi/compiler/CompileScope.java), [export implementation](https://github.com/JetBrains/intellij-community/blob/idea/263.7307.200/java/compiler/openapi/src/com/intellij/openapi/compiler/ExportableUserDataHolderBase.java), [CompileDriver](https://github.com/JetBrains/intellij-community/blob/idea/263.7307.200/java/compiler/impl/src/com/intellij/compiler/impl/CompileDriver.java), [JPS context](https://github.com/JetBrains/intellij-community/blob/idea/263.7307.200/jps/jps-builders/src/org/jetbrains/jps/incremental/CompileContext.java).

Implementable calls in the existing `GwtBuildTargetScopeProvider.getBuildTargetScopes(...)`:

```java
List<RemoteRepositoryDescription> repositories =
  RemoteRepositoriesConfiguration.getInstance(project).getRepositories();
baseScope.putUserData(REPOSITORY_CONFIGURATION_KEY, encodeRepositories(repositories));
```

`REPOSITORY_CONFIGURATION_KEY` should be `Key<String>` with a plugin-specific stable name. Encode an explicit schema version and ordered `{id,url}` entries using a plugin-owned DTO/codec; optionally carry name and snapshot policy if deliberately supported. Construct a fresh snapshot on every invocation, before any empty-facet early return. In JPS read `context.getBuilderParameter(REPOSITORY_CONFIGURATION_PARAMETER)` and create public Aether repositories with the original IDs and URLs. Read/validate once per compile context, and cache any manager there rather than in process-global state. Unknown/malformed versions should cause a useful configuration error, not silent fallback to Maven Central. Snapshot size and string lengths should be bounded.

The IDE model's `getInstance`, `getRepositories`, repository constructor and `getId`/`getUrl` are public and unannotated. `RemoteRepositoriesConfiguration.setRepositories` substitutes defaults for an empty list; its saved form includes id/name/url. Sources: [IDE configuration](https://github.com/JetBrains/intellij-community/blob/idea/263.7307.200/java/java-impl/src/com/intellij/jarRepository/RemoteRepositoriesConfiguration.java), [IDE repository description](https://github.com/JetBrains/intellij-community/blob/idea/263.7307.200/java/openapi/src/com/intellij/jarRepository/RemoteRepositoryDescription.java).

No new IDE extension is needed if the existing scope provider owns this snapshot. Its existing registration is:

```xml
<compiler.buildTargetScopeProvider
    implementation="org.randombits.intellij.gwt.build.GwtBuildTargetScopeProvider"/>
```

An alternative public `CompileTask` registered with `<compiler.task execute="BEFORE" implementation="..."/>` runs before external compilation and can put data on `context.getCompileScope()`; this is useful for work unsuitable for a read-locked scope-provider callback. Repository list snapshotting itself requires no filesystem or credential access. See [CompileTask contract and registration](https://github.com/JetBrains/intellij-community/blob/idea/263.7307.200/java/compiler/openapi/src/com/intellij/openapi/compiler/CompileTask.java) and [CompileDriver ordering](https://github.com/JetBrains/intellij-community/blob/idea/263.7307.200/java/compiler/impl/src/com/intellij/compiler/impl/CompileDriver.java).

The driver's up-to-date-only check intentionally supplies an empty parameter map. Do not resolve dependencies during that check. Verify that normal explicit make, rebuild, artifact compilation and auto-make paths invoke this provider and transmit its DTO; the inspected source establishes the normal `CompileDriver` path, not every third-party build invoker.

## Why the launch provider is unnecessary

`BuildProcessParametersProvider` itself and `getVMArguments`, `getPathParameters`, `getAdditionalPluginPaths` are public. Only `getPrependedClassPath` is Internal. Registration is `<buildProcess.parametersProvider implementation="..."/>`; the SDK declares it as a project-level EP. The native manager consumes the JVM/path arguments and copies additional plugin paths in `launchBuildProcess`. `scheduleBuild` can take an already preloaded process before launching a new one; a provider EP change listener cancels preloaded processes, but that does not establish a configuration-value comparison on every build. Therefore a fresh DTO should travel in the actual build request, independently of process launch/preloading. Sources: [provider API](https://github.com/JetBrains/intellij-community/blob/idea/263.7307.200/java/compiler/impl/src/com/intellij/compiler/server/BuildProcessParametersProvider.java), [BuildManager](https://github.com/JetBrains/intellij-community/blob/idea/263.7307.200/java/compiler/impl/src/com/intellij/compiler/server/BuildManager.java). The project-level EP declaration was also inspected in SDK `plugins/java/lib/java-impl.jar!/META-INF/plugin.xml`.

This removes temporary-file ownership, atomic replacement, cross-build file races and bridge-file path mapping from the design. Actual repository paths for a remote build still must belong to the JPS environment; avoiding a bridge file does not establish general remote repository support.

## Standalone configuration without Internal repository types

The existing `JpsGwtModelSerializerExtension` already overrides public `getProjectExtensionSerializers()`. Add a plugin serializer constructed as:

```java
new JpsProjectExtensionSerializer("jarRepositories.xml", "RemoteRepositoriesConfiguration") {
  @Override public void loadExtension(JpsProject project, Element componentTag) { /* DTO */ }
  @Override public void loadExtensionWithDefaultSettings(JpsProject project) { /* defaults */ }
};
```

The exact loader iterates every extension and every returned project serializer, so this does not require taking ownership from the platform's repository serializer. Parse the same `remote-repository/option` children, retaining entries with non-null id and URL, and use native defaults if no valid entries exist. Store the result in a plugin-owned project extension, or another explicitly project-scoped store; do not access native `JpsRemoteRepositoriesConfiguration`. The platform loader supplies directory and file-based configuration handling. The IDE DTO takes precedence over this persisted snapshot for a build because it captures current IDE state. Programmatically constructed standalone models should support explicit plugin configuration and documented native defaults when neither source exists. Sources: [serializer extension](https://github.com/JetBrains/intellij-community/blob/idea/263.7307.200/jps/model-serialization/src/org/jetbrains/jps/model/serialization/JpsModelSerializerExtension.java), [project serializer](https://github.com/JetBrains/intellij-community/blob/idea/263.7307.200/jps/model-serialization/src/org/jetbrains/jps/model/serialization/JpsProjectExtensionSerializer.java), [base callbacks](https://github.com/JetBrains/intellij-community/blob/idea/263.7307.200/jps/model-serialization/src/org/jetbrains/jps/model/serialization/JpsElementExtensionSerializerBase.java), [native repository serializer](https://github.com/JetBrains/intellij-community/blob/idea/263.7307.200/jps/model-serialization/src/org/jetbrains/jps/model/serialization/jarRepository/JpsRemoteRepositoriesConfigurationSerializer.java), [loader iteration](https://github.com/JetBrains/intellij-community/blob/idea/263.7307.200/jps/model-serialization/src/org/jetbrains/jps/model/serialization/JpsProjectLoader.java).

Do not call the base serializer's `getConfigFileName` or `getComponentName`: those getters are Internal. Do not override its obsolete `saveExtension`; JPS does not save these settings. Supporting this component in a public custom serializer is a configuration-format dependency that needs tests when upgrading IDEA.

## Local repository and authentication parity

Public `JpsModelSerializationDataService.getPathVariableValue(global, "MAVEN_REPOSITORY")` supplies the global user variable through a public string API. It first checks built-in system macros, then user variables; `MAVEN_REPOSITORY` is the native dependency resolver's user-defined variable. `getBaseDirectoryPath(JpsProject)` is also public if a caller needs the standalone project directory. In contrast, `getPathVariablesConfiguration` returns an Internal type and is itself Internal. Source: [serialization data service](https://github.com/JetBrains/intellij-community/blob/idea/263.7307.200/jps/model-serialization/src/org/jetbrains/jps/model/serialization/JpsModelSerializationDataService.java).

Reproduce the current native fallback in plugin code, using standard Java XML/path/environment APIs or already verified public utility APIs. Native behavior is more specific than generic Maven behavior:

1. Use the global `MAVEN_REPOSITORY` user variable if non-null.
2. Otherwise parse `MAVEN_OPTS` for `-Dmaven.repo.local` (including double-quoted values; last property wins).
3. Otherwise choose the user `~/.m2/settings.xml` if that file exists, else the discovered global settings file. Read `localRepository`; fall back to `~/.m2/repository` if absent/unreadable. An existing user file without `localRepository` does **not** fall through to global `localRepository` in the native implementation.
4. Native global discovery checks `/opt/homebrew/Cellar/maven/Current/libexec/conf/settings.xml` on macOS, then `/usr/share/maven/conf/settings.xml` on macOS/Linux. Do not silently replace these with `M2_HOME`/`MAVEN_HOME` semantics under the claim of parity.

Native authentication precedence is: the JPS JVM system property `org.jetbrains.jps.incremental.dependencies.resolution.remote.repository.auth.` + repository ID; then `JpsServiceManager.getInstance().getExtensions(DependencyAuthenticationDataProvider.class)` in extension order, queried with URL; then matching server ID from Maven XML. Load global server credentials before user credentials so the latter overwrite matching IDs. The native XML reader accepts empty or Maven SETTINGS namespaces, skips incomplete servers and unreadable settings, and does not implement encrypted password decryption. Native system-property parsing uses `split(":")` and requires exactly two tokens, including its existing colon/empty-value limitations. Sources: [native resolver acquisition and precedence](https://github.com/JetBrains/intellij-community/blob/idea/263.7307.200/jps/jps-builders/src/org/jetbrains/jps/incremental/dependencies/DependencyResolvingBuilder.java), [native Maven settings behavior](https://github.com/JetBrains/intellij-community/blob/idea/263.7307.200/jps/model-serialization/src/org/jetbrains/jps/model/serialization/JpsMavenSettings.java).

`DependencyAuthenticationDataProvider` and its `AuthenticationData` are public, with the enclosing provider explicitly Experimental; `JpsServiceManager.getExtensions` is public. Retaining this preserves JPS authentication extensions. IDE `JarRepositoryAuthenticationDataProvider` is also public Experimental, but using IDE providers instead would be a different provider model and introduces secret transport. Its convenience `obtainAuthenticationData` function is Kotlin `internal`; do not call that generated JVM method simply because javap exposes it. Sources: [JPS provider](https://github.com/JetBrains/intellij-community/blob/idea/263.7307.200/jps/jps-builders/src/org/jetbrains/jps/incremental/dependencies/DependencyAuthenticationDataProvider.java), [service manager](https://github.com/JetBrains/intellij-community/blob/idea/263.7307.200/jps/model-api/src/org/jetbrains/jps/service/JpsServiceManager.java), [IDE providers](https://github.com/JetBrains/intellij-community/blob/idea/263.7307.200/java/idea-ui/src/com/intellij/jarRepository/JarRepositoryAuthenticationDataProvider.kt).

Do not use `JarRepositoryManager.getJPSLocalMavenRepositoryForIdeaProject(project)` as an equivalent native fallback: it is public Experimental, but falls back through deprecated `getLocalRepositoryPath`, which ignores Maven settings and `MAVEN_OPTS`. Its own documentation flags its limitations. Source: [JarRepositoryManager](https://github.com/JetBrains/intellij-community/blob/idea/263.7307.200/java/idea-ui/src/com/intellij/jarRepository/JarRepositoryManager.java).

Resolve credentials at acquisition time in JPS; never put them in DTOs, project state, cache metadata, VM arguments or logs. Do not log raw settings XML, credentials, system-property values, encoded DTOs or repository objects/URLs containing userinfo. This investigation did not open any real user settings or credentials.

## Acquisition, retry, cancellation and cache lifetime

Exact binary inspection confirms public unannotated `ArtifactRepositoryManager(File,List<RemoteRepository>,ProgressConsumer,Retry)`, `createRemoteRepository(id,url,authenticationData)`, the nested authentication constructor and `resolveDependency(...)`. The manager's `PRIORITY_REPOSITORY_URL_PROPERTY` constant is Internal: do not reference it. Public `RetryProvider.disabled()` and `withExponentialBackOff(...)` preserve current policy; retain native property names as plugin-owned string literals rather than referencing the Internal resolver's constants. Defaults when retry is enabled are 1000 ms initial delay, 15-minute backoff cap, 10 attempts. Forward progress through `context.processMessage(new ProgressMessage(message))` and cancellation through `context.getCancelStatus().isCanceled()` in `ProgressConsumer`. These are the native acquisition calls shown in the matching [resolver source](https://github.com/JetBrains/intellij-community/blob/idea/263.7307.200/jps/jps-builders/src/org/jetbrains/jps/incremental/dependencies/DependencyResolvingBuilder.java).

Preserve repository order and IDs. For strict native parity use the same authentication-enabled repository factory overload as the native JPS helper; native JPS does not transfer the IDE-only snapshot-policy flag. Adding stricter snapshot behavior would be a separate intentional change. Keep managers per compilation context so repository/settings changes apply to subsequent builds. Cancellation must propagate through the caller's existing failure handling; broad `catch (Exception)` must not turn cancellation into an apparently successful fallback. Existing dependency-path cache invalidation should be reviewed separately: changing repository/auth config should not reuse a manager from another build, while already cached complete artifacts may legitimately need no new download.

## Annotation evidence and required validation

Inspected `javap -p -v` for the actual owning SDK classes and method annotation blocks, not Java visibility alone. The native `org.jetbrains.jps.model.jarRepository` package has `@ApiStatus.Internal` in both matching-tag [package-info.java](https://github.com/JetBrains/intellij-community/blob/idea/263.7307.200/jps/model-api/src/org/jetbrains/jps/model/jarRepository/package-info.java) and SDK `lib/jps-model.jar` package-info bytecode. No package-info class applies to the public bridge/provider/model-service packages in their owning SDK jars. The relevant public methods above have no Internal annotation; noted Experimental and deprecated qualifications remain real. SDK owners include `lib/jps-model.jar`, `plugins/java/lib/modules/intellij.java.{jar,impl.jar,ui.jar,compiler.jar,compiler.impl.jar}`, `plugins/java/lib/modules/intellij.platform.jps.build.jar`, and `plugins/java-aetherDependencyResolver-plugin/lib/modules/intellij.java.aetherDependencyResolver.jar`.

Required implementation checks: versioned DTO roundtrip with Unicode and delimiter-containing values; ordered custom repositories and duplicate IDs; live IDE configuration changes on consecutive/preloaded builds; default and standalone serialized configuration (including file-based projects); local-repository precedence matrix using temporary settings only; global/user authentication override, system-property override, public provider precedence and malformed property behavior; authenticated local HTTP repository download with synthetic credentials; retry, progress and cancellation; missing/invalid configuration failures; no credential leakage into logs/project files/DTO/cache metadata; and strict Plugin Verifier with no new Internal findings. Run the real GWT/JPS smoke suite after replacing acquisition. This research ran source/bytecode inspection only and made no production-code changes.

## Implemented checks

The per-build DTO, public IDE snapshot, parallel standalone serializer, public string path lookup and plugin-owned native policy are implemented. Focused tests pass ordered/versioned payloads and rejection, settings precedence, actual directory/.ipr loading, changing IDE snapshots, and loopback authenticated resolution through property/provider/settings credentials with cancellation. The real JPS scenario changes builder parameters within one process and verifies malformed configuration produces an error without echoing the payload; valid subsequent configuration succeeds. Runtime and verifier results are recorded in the Marketplace guide. Programmatic standalone models must set the plugin configuration or builder parameter when they need custom repositories; the Internal native repository model is not read.
